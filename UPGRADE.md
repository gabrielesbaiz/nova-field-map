# Upgrading

## 2.x to 3.0

Most 2.x resources upgrade without an edit. Three things do not.

### 1. Popup content is escaped by default

**This is a security fix, and it is the change most likely to alter what you
see on screen.**

Leaflet's `bindPopup()` renders a string as raw HTML. 2.x passed the value of a
feature property to it untouched, so any user able to write that column could
run JavaScript in an authenticated administrator's Nova session.

In 3.0, popup and tooltip bodies are escaped in PHP. A popup whose content is
`<b>Head office</b>` now renders that as literal text.

If the content is trusted, opt back in:

```php
FieldMap::make('Branches', 'coordinates')
    ->popup('description')
    ->allowHtmlPopups()
```

Even then the browser sanitises the markup with DOMPurify. To turn that off as
well — which is a decision, not a default — set `popups.sanitize` to `false` in
the published config.

Where the markup is generated by your own code rather than stored, prefer
returning a view instead; it is trusted without opening the property up:

```php
->popupUsing(fn (array $feature) => view('nova.branch-popup', $feature['properties']))
```

Tooltips have no HTML path at all. `->tooltip()` is always escaped.

### 2. PHP 8.2 and Nova 5

| | 2.x | 3.0 |
|---|---|---|
| PHP | 8.0 | 8.2 |
| Laravel | 10, 11, 12 | 11, 12, 13 |
| Nova | 4 | 5 |

There is no Nova 4 build of 3.0. Stay on 2.x until you upgrade Nova.

### 3. Four methods were removed

| Removed | Why | Instead |
|---|---|---|
| `exportImage()` | Rasterising tile layers to PNG is blocked by canvas tainting on most providers. A button that fails on most installs is worse than no button | `exportData()` for GeoJSON and GPX |
| `minimap()` | Needs another Leaflet plugin for a feature few maps used | — |
| `measure()` | Same | `route()` reports distance; `scaleControl()` gives a scale bar |
| `popupActions()` | Dispatching a Nova action from inside a Leaflet popup needs more of Nova's form runtime than a popup can carry | `linkToResource()`, then run the action on the detail page |

Calls to these now raise `BadMethodCallException` rather than silently doing
nothing.

## What still works unchanged

Everything else. These are all shimmed and covered by a dedicated test suite:

```php
// The 2.x class and provider names.
use Gabrielesbaiz\NovaFieldMap\NovaFieldMap;          // extends FieldMap
NovaFieldMapServiceProvider::class;                    // extends FieldMapServiceProvider

// The 2.x LatLon chain.
NovaFieldMap::make('Location')
    ->type('LatLon')
    ->point($this->my_latitude, $this->my_longitude)
    ->popup('I am a Popup')          // literal text, as in 2.x
    ->height('400px');

// The 2.x GeoJson chain.
NovaFieldMap::make('Area')
    ->type('GeoJson')
    ->geoJson($this->geojson_column)
    ->popup('popup');                // a property name, as in 2.x

// Markers and Google.
NovaFieldMap::make('Location')
    ->markerIcon('/images/marker-icon.png', [100, 100], [50, 50])
    ->googleApiKey('...')
    ->googleMapType('satellite');
```

Note that `popup()` kept **both** of its 2.x meanings: under `type('LatLon')`
the argument is the popup's literal text, and under `type('GeoJson')` it names
a feature property. Without a `type()` call — that is, in new code — it always
names a property.

`type()` and the class aliases are deprecated and are removed in 4.0.

## What you probably want to change anyway

None of this is required, but 3.0 exists to make these possible.

### Let the field read its own attribute

2.x could not resolve a model attribute, so every resource pushed data in at
`make()` time:

```php
// 2.x
NovaFieldMap::make('Location')
    ->type('LatLon')
    ->point($this->my_latitude, $this->my_longitude)
```

```php
// 3.0
FieldMap::make('Location')
    ->coordinates('my_latitude', 'my_longitude')
```

Or, for a single column holding coordinates in any recognised shape:

```php
FieldMap::make('Location', 'coordinates')
```

This is what makes `dependsOn()`, `resolveUsing()`, filling and validation work
on the field at all.

### Make it editable

2.x forced `showOnUpdate` to `false` and shipped an inert text input:

```php
FieldMap::make('Location', 'coordinates')
    ->editable()
    ->geocoder()
```

### Adopt the map without a migration

If two number fields already own the columns, the map can drive them and write
nothing itself:

```php
FieldMap::make('Location')
    ->coordinates('lat', 'lng')
    ->syncTo('lat', 'lng'),

Number::make('Lat'),
Number::make('Lng'),
```

## After upgrading

```bash
composer update gabrielesbaiz/nova-field-map
php artisan vendor:publish --tag=nova-field-map-config --force   # if you published it
php artisan view:clear && php artisan cache:clear
php artisan nova-field-map:doctor
```

`view:clear` matters: Nova caches its script manifest, and a stale one keeps
serving the 2.x bundle. If you see `Bounds are not valid` in the console after
upgrading, that is what happened.

## Fixed in 3.0

Bugs from 2.x that need no action from you:

- Two layer switchers rendered, because the same control was added twice.
- Two map fields on one page shared a marker icon, because icon options were
  written to `L.Icon.Default.prototype`.
- Maps were never removed on navigation, leaking a Leaflet instance and its
  handlers on every Inertia page change.
- A record with no geometry threw `Bounds are not valid` and rendered blank.
- A malformed GeoJSON string was passed through to Leaflet and silently
  produced an empty map.
- Selecting the Google layer before its SDK finished loading threw.
